TOKEN POSITIONS: IMPORTANT DISTINCTION
- token_indices is the zero-based whitespace-token location inside a cue.
- SubtitleWord.position_in_cue is the one-based occurrence count of the EXACT
  same token string inside that cue, not the token index.
- Example: "head head! head head," has token indices 0, 1, 2, 3 and corresponding
  position_in_cue values 1, 1, 2, 1. Case, punctuation, and markup matter.
- The backend derives this occurrence count from the saved subtitle; never copy
  token_indices into position_in_cue. The manual editor follows the same rule.
- Validate against the current subtitle context, preserving exact token strings,
  line breaks, timings, and the SHA256 of the actual subtitle bytes.

WORKFLOW AT A GLANCE
1. User provides the actual section subtitle file, preferably with the wizard's
   downloaded subtitle-context JSON.
2. Assistant selects B2+ single-word occurrences and advanced contextual senses.
   Inside expressions, phrasal verbs, and idioms, select only the main subtitle
   token. Scrape only its main dictionary headword; see CURRENT USER RULES above.
3. Assistant returns a suggestions JSON ARRAY with exact cue/token information,
   main dictionary headword, scrape_term, and main-word longman_url. Never verify
   URLs or add intended_meaning or url_verification fields.
4. User uploads/pastes this array into step 1 of Bulk Mappings.
5. Step 2 presents each occurrence with its dialogue context. User chooses Keep
   or Remove, with Previous/Next navigation. Navigation alone is not acceptance.
   Review is optional: Continue to dictionary or the Prepare dictionary step
   automatically keeps all unreviewed occurrences and preserves removals.
6. Step 3 checks the dictionary and scrapes missing words sequentially, with logs.
7. Step 4 exports final accepted suggestions and a compact mappings template.
8. User gives the accepted-words export to the assistant. Assistant reads the
   actual database definitions and examples, selects matching existing sense IDs, and returns
   the populated mapping_template OBJECT as a separate final JSON file.
9. User uploads that final JSON, previews it, and creates mappings in the wizard.
   Existing mappings must never be overwritten.

REVIEW AND SKIPPING: IMPLEMENTED IN SUBSEQUENT WORK
- Continue to dictionary is enabled during review without individual confirmation.
  It marks remaining undecided suggestions Keep and preserves explicit removals.
  The Prepare dictionary navigation step uses the same behavior after import.
  If all suggestions were removed, the next step explains that at least one must
  be kept; it does not scrape an empty selection.
- Confirmed WordNotFoundError responses now return HTTP 404 plus
  {"code": "word_not_found"}. The frontend recognizes this combination, logs
  "no entry found in Longman. Skipped all occurrences.", removes all occurrences
  of that headword from the accepted selection, and continues automatically.
  They are excluded from sense exports. Generic 404s are not silently skipped.
- All other per-word failures are logged, added to the failed-word list, and
  skipped automatically. They never pause preparation. All occurrences of the
  failed headword are excluded from export until a successful retry. The user
  can use Retry failed words afterward. No manual skip button is required.
- These selection changes and logs are still in-memory wizard state.

RETRIES AND STOP: IMPLEMENTED
User frequently got 502 errors from scraping; manual retries often succeeded.
Automatic retries were added to the frontend preparation loop:
- Three retries after the original attempt: waits of 3, 8, and 15 seconds.
- Retry logs show the word, underlying error, delay, and retry number.
- Each attempt rechecks dictionary existence before scraping.
- Only HTTP 502 errors with JSON retryable: true retry automatically.
- Backend adds that flag only for PageLoadError and AudioDownloadError, and logs
  the actual exception. Exhausted retries record the failed word and continue.
  Other per-word errors skip immediately and continue without automatic retries.
- Ambiguous network/lost-response errors do NOT automatically retry, because a
  write may have succeeded on the server. Generic 502 proxy responses without
  the explicit flag also do not retry. This is intentional.
- "Stop retries / preparation" cancels pending waits immediately and prevents
  subsequent retries/words. It does not abort an in-flight request; that request
  can finish and its successful entries are retained. UI shows "Stopping...".
- Unmount signals stop and cancels waits. No concurrent scrape requests are
  intentionally started by this wizard.
- A fixed delay between different successful words was discussed but NOT added.

PERSISTENCE
Successful scrapes save dictionary records and audio immediately. A later error
or closing the browser does not undo completed words. In-flight requests may
finish even after closing the page. On return, database lookup skips saved words.
Wizard state is in React memory, not persisted across browser sessions. The user
must reimport suggestions and review decisions after closing/reloading. The
accepted-suggestions download helps retain the selection, but reimport still
starts a fresh review. Exported final mappings can be loaded directly in step 4.
Do not claim that review decisions or logs automatically survive a reload.

# Bulk Mappings

Open a section in the admin panel and choose **Bulk Mappings**. The original
mapping editor remains available and unchanged.

## Authoring workflow

1. Upload the final subtitle file to the section using the existing section editor.
2. In Bulk Mappings, download **subtitle context**. Give that JSON and, optionally,
   the subtitle file to the assistant in chat. The context contains instructions,
   the subtitle fingerprint, exact cue text, timing, and canonical tokens.
3. Ask for B2+ single-word selections and advanced senses. For expressions,
   phrasal verbs, and idioms, select ONLY the main subtitle word, and look up/scrape
   ONLY the main dictionary headword. Do not generate per-word meaning explanations.
   Never check URLs online; do not add a URL-verification field or status.
4. Upload or paste the suggestions array. Optionally review with **Keep and next**
   or **Remove and next**. **Continue to dictionary** or **Prepare dictionary**
   keeps all unreviewed occurrences and preserves removals. Previous/Next alone
   does not imply acceptance. Removed suggestions remain revisitable.
5. Optionally download accepted suggestions as a checkpoint. Reimporting this file
   starts a new review, but does not alter saved dictionary entries or mappings.
6. Prepare dictionary entries. Lookup is case-insensitive by canonical headword,
   across all parts of speech. Missing headwords use the supplied scrape term via
   the existing development-only scraper. Only one request runs at a time, terms
   are deduplicated, and successful work is preserved. Confirmed page-loading and
   audio-download failures retry up to three times after 3, 8, and 15 seconds,
   checking the dictionary before each attempt. Other failures and exhausted retries
   are logged and skipped automatically; preparation continues with the next word.
   Failed words can be retried afterward and remain excluded from sense exports
   until successfully prepared. Confirmed word-not-found responses are also logged
   and skipped, removing all occurrences from the accepted selection.
   Stop cancels pending waits immediately and lets an active
   request finish before pausing. Keep the page open while requests run.
7. Download accepted words for sense selection after preparing the dictionary.
   This exports the final accepted suggestions, excluding removals and skipped
   words, plus a compact mapping template. Give it to the assistant, who reads
   senses from the dictionary database by dictionary_word and selects meanings
   matching the subtitle context. Database access is read-only for this step.
8. Upload the returned schema-version-2 mapping object, preview, then create
   mappings. No review token, review ID, saved review record, or browser session
   is needed. Keep section_id and subtitle_sha256 unchanged. Older version-1
   files must be regenerated; their suggestion IDs do not identify locations.

No model/AI API calls happen inside the application. Language analysis happens
in chat. URL verification is never performed. No intended_meaning or url_verification fields are generated.
The application validates URL shape and host, not the dictionary page contents.

## Suggestions format

The initial file is a JSON **array**. One object selects one main-word token,
even when its contextual meaning comes from a larger term. The hash
below is a placeholder; copy the real `subtitle_sha256` from the context export.

```json
[
  {
    "id": "take-off-1",
    "subtitle_sha256": "COPY_THE_64_CHARACTER_SHA256_FROM_CONTEXT",
    "subtitle_word": "take",
    "cue_id": 1,
    "cue_text": "We take off, then take off.",
    "start_time": 1,
    "end_time": 4,
    "token_indices": [1],
    "dictionary_word": "take",
    "scrape_term": "take",
    "longman_url": "https://www.ldoceonline.com/dictionary/take"
  }
]
```

The URL above illustrates the format, not a guarantee that this dictionary page is
the correct entry. Use only the main headword, leave its URL unchecked as
requested, and later select the matching take-off sense under take if
available in the current database. Do not scrape take-off separately.

Indices are zero-based whitespace-token indices **within a cue**. Preserve case,
punctuation, and cue line breaks. They are not `position_in_cue`: that database
field counts occurrences of an exact token string, starting at one. The backend
derives it, as well as neighboring cue times, from the saved subtitle file.

Both VTT and SRT-style timing are accepted by the context parser. Work from the
actual saved section file: reformatting or changing its bytes changes its hash.
Cross-cue phrases are not supported in this initial bulk mappings format; use the existing
editor for these. Suggestion files accept up to 2,000 occurrences (browser file
uploads are limited to 5 MB).

## Final mappings format

Return the `mapping_template` object provided by the export, filling `sense_ids`:

```json
{
  "schema_version": 2,
  "section_id": 3,
  "subtitle_sha256": "COPY_FROM_EXPORT",
  "mappings": [
    { "cue_id": 1, "token_indices": [1], "sense_ids": [42] }
  ]
}
```

Use actual database sense IDs matching the context; `42` is illustrative. At least one mapping is needed.
Keep scraped words with stored senses, using the nearest meaning when an exact
match is unavailable. Discuss unavoidable omissions with the user before creating
the final JSON. Do not generate a separate omission report unless requested.
The server cannot count
omissions without the original selection; preview reports ready/skipped only.
Keep subtitle metadata and locations unchanged. Import validates the entire file before any
write, checks current subtitles and sense availability, and skips a whole phrase
when any selected token is already mapped. Overlaps inside the same batch are also
skipped in input order. Reimporting an already applied file creates no duplicates.
It never deletes or updates existing mappings.

All bulk mappings endpoints require a staff account. The existing scraper stays
development-only; `NEXT_PUBLIC_ENABLE_SCRAPER=true` enables its wizard button path.
No new model or migration is needed for this workflow.
