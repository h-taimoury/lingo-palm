Status: WORK IN PROGRESS. Major frontend architecture and product
decisions have been settled, but this is still a planning recap rather
than literal step-by-step build instructions. Remaining OPEN / NEEDS
VERIFICATION items should be resolved before code generation.

Companion files this recap assumes are also available to whoever reads
it: - lingo_palm_backend_ai_context.txt (Django backend API reference) -
lingo_palm_ai_context.txt (short project/stack overview) -
Project_Concept.txt (full product concept doc) - The old Next.js+Mongo
codebase (reference only, for old UI patterns — its DATA MODEL is now

IMPORTANT: verify the context files above are actually up to date with

  -----------------------------------------------------------------------
  1. PROJECT CONTEXT (brief — see companion docs for full detail)
  -----------------------------------------------------------------------
  - English-learning platform: learners watch videos with interactive
  subtitles; clicking a highlighted subtitle word/phrase shows the
  specific dictionary Sense(s) relevant to that occurrence. - Backend:
  Django + DRF, cookie-based JWT auth (httpOnly access_token /
  refresh_token cookies + readable csrftoken cookie), apps: users,
  dictionary (Entry/Sense), courses (Course→Section→WordSenseMapping→
  SubtitleWord), my_vocabulary (per-user learned-sense tracking),
  scraper_admin (dev-only, scrapes Longman dictionary). - This is a
  REBUILD of a previous all-in-Next.js+Mongo prototype (that old code is
  provided only as a UI/UX reference — its data model, auth system, and
  most of its dependencies no longer apply).

  The backend is the application’s real backend and source of truth
  for: - authentication - authorization - business rules - dictionary
  data - course/section data - learner vocabulary state - course/section
  progress - mutations and persistence

  Next.js is primarily the frontend/rendering application. Do not
  recreate backend business logic or create an unnecessary second backend
  layer in Next.js.

  3. DOMAINS & DEPLOYMENT ASSUMPTIONS (decided)
  -----------------------------------------------------------------------
  - Frontend: lingopalm.com - Backend: api.lingopalm.com - Same root
  domain — this materially simplifies the cookie/auth story. - Local dev
  uses localhost:3000 / localhost:8000.

  BACKEND PREREQUISITE: Django must set access_token / refresh_token /
  csrftoken cookies with Domain=.lingopalm.com in production settings,
  and host-only (no Domain attribute) in development settings.

  The frontend does not store or manipulate the JWT access/refresh tokens
  in JavaScript. They remain httpOnly cookies.

  Because the browser is making direct requests from the frontend origin
  to the backend origin, client-side API calls MUST use:

  credentials: “include”

  The backend’s CSRF requirements also apply to browser-side mutations.

4. ARCHITECTURE (decided)

The fundamental architecture is:

    Next.js frontend
          |
          +-------------------------------+
          |                               |
    Server Components              Client Components
          |                               |
          |                         centralized apiClient
          |                               |
          +---------------+---------------+
                          |
                       Django API
                          |
                       database

4.1 SERVER COMPONENTS — DEFAULT

Every page is a Server Component by default.

A page should fetch its initial/read-heavy data directly from Django
server-to-server.

Conceptually:

    Server Component
        ↓
    read cookies from next/headers
        ↓
    forward the relevant Cookie header to Django
        ↓
    render page
        ↓
    pass fetched data to Client Components as props

Use Server Components as much as possible.

Do NOT turn an entire page into a Client Component merely because one
small part of the page needs interactivity.

Preferred pattern:

    page.tsx                         ← Server Component
        |
        +-- data fetching
        |
        +-- InteractiveWidget.tsx   ← Client Component
        |
        +-- AnotherInteractive.tsx  ← Client Component

4.2 CLIENT COMPONENTS — ONLY WHERE INTERACTION IS NEEDED

Use Client Components for things such as:

-   video player
-   interactive subtitle highlighting
-   sense popup/modal
-   forms requiring browser-side interaction
-   drag-and-drop
-   live/type-ahead search
-   multi-select controls
-   “mark as learned” / vocabulary actions
-   interactive admin editor
-   client-only UI state

Client Components call Django DIRECTLY.

They do NOT normally call a Next.js API route or Server Action as a
proxy.

Example:

    Client Component
        ↓
    apiClient
        ↓
    Django API

4.3 MUTATION PATTERN — DECIDED

All normal backend mutations follow the same rule:

    Client Component
        ↓
    centralized apiClient
        ↓
    Django API

Examples:

-   create/edit/delete course
-   create/edit/delete section
-   create/edit/delete word-sense mapping
-   dictionary mutations
-   mark senses learned
-   set senses already known
-   vocabulary bulk actions
-   login/register/logout
-   profile mutations
-   scraper actions

The reason is architectural:

Django is already a dedicated backend/API.

If Next.js were being used as a fullstack application with its own
database/business logic, Server Actions would be a strong choice for
mutations.

That is NOT the architecture here.

Using Server Actions as a generic proxy:

    Browser
       ↓
    Next.js Server Action
       ↓
    Django

would add another backend layer and another place to maintain request
logic, authentication behavior, error handling, and data flow, while
providing little benefit.

Therefore:

    Browser
       ↓
    Django

is the normal mutation path.

Server Actions are NOT forbidden. They may still be used for a very
specific Next.js-only concern where they genuinely provide value, but
they are not the application’s general mutation mechanism.

4.4 AFTER MUTATIONS

After a successful client-side mutation, normally use:

    router.refresh()

when the enclosing Server Component needs to fetch the updated data
again.

Do not introduce a complicated client-side global state system just to
keep server-rendered data synchronized unless a particular feature
actually needs it.

4.5 MIDDLEWARE — DECIDED ROLE

middleware.ts should remain lightweight.

Its primary frontend responsibility is route protection:

    /learning/*
    /teaching/*

For these routes, middleware may perform a cheap check for the presence
of the authentication cookie and redirect obviously unauthenticated
visitors to /login.

This is NOT full authentication validation and is NOT a security
boundary.

Django remains the real authority for authentication and authorization.

IMPORTANT: Middleware does NOT perform token refresh.

We explicitly rejected “refresh on every request” middleware behavior
because it can cause unnecessary backend calls, couples middleware to
authentication refresh behavior, and is unnecessarily complicated given
the dedicated Django backend.

4.6 TOKEN REFRESH FLOW — DECIDED

The backend provides:

    access_token  → approximately 1 day
    refresh_token → approximately 2 weeks

and:

    POST /api/users/refresh/

The frontend handles expiry REACTIVELY.

Do NOT refresh based only on timers. Do NOT make middleware call the
refresh endpoint on every request.

Instead:

    Client API request
          ↓
    Django
          ↓
       401?
       /   \
     no     yes
     |       |

return refresh | retry original request | return

The refresh/retry behavior belongs in the centralized client-side
apiClient/fetcher.

The apiClient should:

1.  Make the original request.
2.  If the response is 401, attempt token refresh.
3.  Retry the original request exactly once after successful refresh.
4.  If refresh fails, treat the session as unauthenticated.
5.  Do not recursively retry forever.

IMPORTANT: CONCURRENT REFRESH LOCKING

Multiple Client Components may make requests simultaneously.

Example:

    request A → 401
    request B → 401
    request C → 401
    request D → 401

They must NOT trigger four independent refresh calls.

Use a single-flight/shared refresh promise:

    request A ──┐
    request B ──┤
    request C ──┼──→ ONE refresh request
    request D ──┘            |
                             ↓
                      all wait for result
                             |
                             ↓
                      retry their requests

Only one refresh operation may be in progress at a time.

The refresh endpoint itself requires the CSRF header, so apiClient must
handle CSRF for the refresh request as well.

Because Django sets the new JWT cookies in the HTTP response and the
browser owns those cookies, the client does not need to read or manually
store the JWT values.

4.7 CSRF — DECIDED

The browser-visible csrftoken cookie is readable by JavaScript.

The centralized client API layer is responsible for:

-   credentials: "include" on requests
-   reading the csrftoken cookie
-   attaching X-CSRFToken to unsafe requests

Unsafe methods:

    POST
    PUT
    PATCH
    DELETE

GET/HEAD/OPTIONS do not require the CSRF header.

Components should NOT implement their own CSRF handling.

They should call the centralized apiClient instead.

Example conceptually:

    apiClient.post("/api/courses/courses/", payload)

not:

    fetch(...)

4.8 API CLIENT RESPONSIBILITIES — DECIDED

The centralized apiClient/fetcher is a core frontend infrastructure
piece.

It should centralize:

-   API base URL
-   credentials: "include"
-   JSON headers
-   CSRF token handling
-   request/response parsing
-   consistent API error handling
-   401 detection
-   reactive refresh
-   refresh locking / single-flight behavior
-   retrying the original request once
-   avoiding infinite refresh/retry loops

Individual components should remain unaware of these authentication
details.

4.9 STAFF-ONLY GATING FOR /teaching/*

The /teaching/* area is a staff/admin UI.

Use app/teaching/layout.tsx as the frontend staff gate.

The layout can fetch:

    GET /api/users/me/

and check:

    is_staff

Non-staff users should be redirected away from /teaching/*.

This is a UX/navigation gate, NOT the security boundary.

Django must continue enforcing is_staff on every protected backend
operation.

Do not rely on the frontend’s is_staff value to secure anything.

The backend is always authoritative.

  5. DATA FETCHING & CACHING STRATEGY (decided)
  -----------------------------------------------------------------------
  The default data-fetching strategy is:

  Server Components ↓ Django ↓ render data into page

  Do NOT make TanStack Query / React Query a global requirement.

  Most application reads belong naturally in Server Components and should
  not be duplicated into a second client-side cache.

  After client-side mutations, use:

  router.refresh()

  when the Server Component should fetch fresh data.

  5.1 WHEN TANSTACK QUERY IS APPROPRIATE

  TanStack Query (React Query) may be used locally when a feature is
  genuinely client-data-heavy.

  Good examples:

  - live/type-ahead dictionary sense search - debounced search - infinite
  scrolling - rapidly changing client-side data - optimistic mutations
  where appropriate - client-side polling if a future feature needs it

  Do not add React Query to every page merely for consistency.

  SWR is not being used as the default library.

  If a client-side server-state library is needed, prefer TanStack Query
  because it provides the mutation/cache/invalidation features that fit
  the more interactive admin use cases better.

  The current plan is to use it only where it actually helps.

12. SECTION DATA & PERSONALIZED HIGHLIGHTING — DECIDED

The section detail response contains:

    word_sense_mappings[]

Each mapping contains:

    senses[]
    subtitle_words[]

Each mapping represents one highlighted teaching unit / phrase.

A mapping can have multiple senses.

Example:

    mapping
       ├── sense A
       ├── sense B
       └── sense C

12.1 HIGHLIGHTING RULE

A mapping remains highlighted if ANY of its linked senses is unlearned.

Equivalent logic:

    mappingIsFullyLearned =
        every linked sense is already learned by the user

    shouldHighlight =
        !mappingIsFullyLearned

Example:

    Mapping:
      sense 1 → learned
      sense 2 → learned
      sense 3 → unlearned

    Result:
      mapping remains highlighted

If all linked senses are learned:

    sense 1 → learned
    sense 2 → learned
    sense 3 → learned

    Result:
      mapping is no longer highlighted.

12.2 LEARNER-SPECIFIC SECTION RESPONSE — DECIDED

The learner frontend uses a dedicated learner-specific section response.

The backend performs the first/personalized filtering of
word_sense_mappings before sending the section data to the frontend.

When a learner loads a section:

    all section mappings
          ↓
    Django checks the user's learning state
          ↓
    remove mappings where ALL related senses are learned
          ↓
    return only mappings that still need highlighting

Therefore the learner section response contains a word_sense_mappings[]
field containing ONLY mappings for which the user has not learned all
related senses.

This filtering is deliberately performed on the backend because:

-   the backend owns the user’s learning state and business rules
-   it reduces the amount of data sent to the frontend
-   the frontend does not need to receive mappings that can never be
    highlighted for this user

For highlighting purposes, a sense counts as learned only when its state
is learned.

Therefore:

    all related senses = learned
        → mapping is excluded from word_sense_mappings[]

    at least one related sense is not learned
        → mapping remains in word_sense_mappings[]

The frontend does NOT need to repeat this personalized filtering.

After receiving the already-filtered word_sense_mappings[], the frontend
only needs to determine which of those mappings belong to the currently
active subtitle cue during playback.

Conceptually:

    load learner section
        ↓
    Django filters personalized mappings
        ↓
    frontend receives only mappings needing highlighting
        ↓
    active cue changes
        ↓
    frontend finds mappings/subtitle words for that cue in memory

Do NOT make a separate client-side request solely to obtain the user’s
learning state for section highlighting.

16. MY VOCABULARY BULK ACTIONS — IMPORTANT

The backend no longer supports selecting an entire Entry or entire word
and expanding that selection to all its senses.

This feature was deliberately removed.

Reason: A learner may know one sense of a common word without knowing
all of its other meanings.

Therefore the frontend MUST provide ONLY:

    manual multi-select of individual Sense IDs

Do NOT build:

-   select whole word
-   select whole Entry
-   “mark all senses of this word”

This is not merely deferred functionality. It has been deliberately
removed from the product design.

22. CORE ARCHITECTURAL PRINCIPLE — FINAL SUMMARY

The frontend should follow this rule:

    USE SERVER COMPONENTS BY DEFAULT.
    USE CLIENT COMPONENTS ONLY FOR INTERACTIVITY.
    TALK TO DJANGO DIRECTLY.
    KEEP DJANGO AS THE REAL BACKEND.
    CENTRALIZE CLIENT-SIDE API AUTH/CSRF/REFRESH LOGIC.
    DO NOT TURN NEXT.JS INTO A SECOND BACKEND.

More concretely:

    Initial page/read data:
        Server Component → Django

    Interactive browser data:
        Client Component → apiClient → Django

    Mutations:
        Client Component → apiClient → Django

    Token refresh:
        apiClient reacts to 401 → Django refresh → retry once

    Concurrent refresh:
        one shared refresh operation; other requests wait

    CSRF:
        apiClient automatically reads csrftoken and sends X-CSRFToken

    Authentication:

Keep the short-lived access token + long-lived refresh token system.

Client-side requests:

- calls Django POST /api/users/refresh/
- retries the original request exactly once

Server Component requests:

- the Route Handler calls Django's refresh endpoint
- it forwards Django's new Set-Cookie headers to the browser
- it redirects the user back to the original URL
- the page loads again with the refreshed access cookie
- if refresh fails, redirect/treat the session as expired and send the user to

  to

Learning from the modal:
- an individual sense can be marked learned using the existing
  set_learned bulk action with a one-item sense_ids array
- do not use optimistic UI initially
- wait for Django to confirm success
- after success, reflect that sense as learned immediately in local modal state
- if all senses associated with that mapping are now learned, remove that

- if the mutation fails, do not remove anything; keep the modal open and show

Playback restoration:
- opening the modal pauses playback
- remember whether the video had been playing immediately before the modal was

Specific-mapping mode:
- clicking a highlighted subtitle word opens ONLY that word's mapping
- clicking any constituent of a multi-word mapping opens that same mapping
- Left/Right and visible arrow buttons move only through that mapping's senses

Mobile/touch behavior:
- tapping a highlighted subtitle word opens only that mapping

26. VIDEO PLAYER INTERNAL ARCHITECTURE — RESOLVED (2026-08-29)
===============================================================================

This section adds implementation-level architecture decisions for the custom
learner video player. It complements the previously settled player UX in 23.8
and the shared VTT pipeline in 23.6. Where older player implementation details
from the prototype conflict with this section, this section is authoritative.

The old player is UX/reference material only. Do NOT reproduce its tightly
coupled internal architecture, large prop surfaces, DOM-driven subtitle data
handling, duplicated media logic, or giant components.

26.1 ZUSTAND — USE IT, BUT KEEP THE STORE PLAYER-SCOPED

Use Zustand for shared reactive video-player state/actions where it removes
prop drilling and makes player components easier to understand.

Do NOT create one application-global singleton video store. Each VideoPlayer
instance must have its own store, preferably created through a player Provider
using a vanilla Zustand store. This avoids coupling separate player instances
and keeps future clip-review/player reuse safe.

Add Zustand to the frontend dependencies/tech stack.

The store may contain shared observable state such as:

    currentTime
    duration
    isPlaying
    isEnded
    isBuffering
    volume
    isMuted
    playbackRate
    isFullscreen
    isTheater
    activeCueId / activeCueIndex

    modalMode              // "closed" | "mapping" | "cue"
    activeMappingId
    activeSenseIndex
    wasPlayingBeforeModal

and player actions/concepts such as:

    play()
    pause()
    togglePlay()
    seekTo()
    seekBy()
    setVolume()
    toggleMute()
    setPlaybackRate()
    toggleTheater()

    openMappingModal()
    openCueModal()
    closeLearningModal()
    nextSense()
    previousSense()

This list is architectural guidance, not a requirement that every field/action
must have exactly these names.

Do NOT put everything into Zustand merely because it is player-related.
In particular, do not automatically store React components, the Hls instance,
or the HTMLVideoElement itself in Zustand.

26.2 HTMLMediaElement REMAINS THE MEDIA SOURCE OF TRUTH

The real <video> / HTMLMediaElement remains the source of truth for actual media
playback. Zustand represents the reactive UI/player state needed by React; it
must not become a competing fake media engine.

Use a small player-controller layer/hook that owns:

    videoRef
    Hls instance / source attachment lifecycle
    media event listeners
    imperative media operations

Conceptually:

    HTMLMediaElement
          <->
    Player Controller
          <->
    Zustand Player Store
          <->
    Controls / Subtitles / Learning Modal

Media events synchronize observable state into the store, for example:

    play                 -> isPlaying = true
    pause                -> isPlaying = false
    timeupdate            -> currentTime
    durationchange        -> duration
    waiting               -> isBuffering = true
    canplay / playing     -> isBuffering = false
    volumechange          -> volume / muted
    ended                 -> isEnded = true

The controller should be the main place where imperative calls such as
video.play(), video.pause(), seeking, source attachment, and cleanup are
coordinated.

26.3 FAST-CHANGING STATE / ZUSTAND SELECTORS

currentTime changes frequently. Do not cause the entire player tree to rerender
on every playback-time update.

Components must subscribe narrowly to the state they need. Avoid broad
subscriptions equivalent to reading the whole store.

Only components/features that genuinely depend on currentTime should subscribe
to it, primarily:
- timeline/progress UI
- current-time display
- active-cue synchronization

Most buttons and static controls should not rerender merely because playback
time changed.

26.4 ACTIVE CUE SYNCHRONIZATION

Because subtitle data is parsed through the shared VTT pipeline, do NOT return
to browser <track> cuechange events as the application's subtitle-data source.

The canonical parsed cue structure should contain the timing/token identity
needed by the player. The player determines the active cue from media playback
time.

Preferred implementation:
- maintain an active cue index during normal forward playback
- advance/backtrack that index as playback crosses cue boundaries
- after a seek or other discontinuous time jump, use a binary-search fallback
  to find the correct cue efficiently

Do not repeatedly perform an unnecessary full linear search over every cue on
every time update.

26.5 SUBTITLE COMPONENT RESPONSIBILITIES

Subtitle rendering components should be mostly presentational.

They consume the already-parsed canonical cue/token structure and mapping data.
They must NOT:
- parse raw VTT
- invent/reconstruct token identity independently
- mutate punctuation to make matching work
- calculate occurrence identity ad hoc in the rendering layer
- construct the subtitle JSX through a state-setting useEffect merely because
  the active cue changed
- use module-level/random counters to assign learner mapping colors

Exact backend matching continues to use the shared deterministic identity:

    cue_id + exact word string + 1-based position_in_cue occurrence counter

The learner player and admin editor must continue sharing the same tokenizer and
canonical subtitle model.

26.6 LEARNER HIGHLIGHT COLOR POLICY

For the learner player, use one consistent visual highlight treatment for
teachable/mapped subtitle occurrences rather than cycling through arbitrary
per-mapping colors.

The interaction itself identifies the mapping when the learner clicks/taps it,
so multiple arbitrary colors are unnecessary and can add visual noise.

The admin mapping editor may still use distinct mapping colors because visually
distinguishing adjacent/existing teaching units is useful during authoring.

26.7 CONTROL VISIBILITY / AUTO-HIDE

Use normal custom-player control behavior rather than tying visibility only to
paused/playing state.

Controls should remain visible when:
- playback is paused
- the user is actively hovering/focusing/interacting with the player controls
- pointer movement or a touch interaction has recently revealed them

While playing and inactive, controls should automatically hide after a short
inactivity delay. Interacting with the player reveals them again.

The exact delay is an implementation/UI-polish value rather than a backend or
product contract.

26.8 VIDEO-SURFACE POINTER / TOUCH BEHAVIOR

Keep the already-settled mobile behavior from 23.8.

For the normal desktop video surface when the learning modal is closed:
- single click on non-interactive video background -> play/pause
- double click left side -> seek backward 10 seconds
- double click right side -> seek forward 10 seconds

Interactive subtitle words and visible controls must handle their own clicks and
must not accidentally trigger the background play/pause/seek behavior.

26.9 LEARNING MODAL OWNS THE INTERACTION WHILE OPEN

While the learning modal is open, underlying player controls/seeking are not
interactive. The modal is the active interaction layer and playback remains
paused according to the already-settled modal rules.

This prevents the media/cue context from changing underneath the learner while
reading or marking senses.

The existing focus-trap and focus-restoration accessibility requirements remain
in force.

26.10 NORMAL ENDING VS FUTURE CLIP PLAYBACK

For ordinary section playback:

    media ended -> show a replay state
    replay       -> seek to 0 and play

Do not overload normal ended behavior with clip-review logic.

If clip playback is implemented later, model clipStart/clipEnd (or an equivalent
playback range) as a separate feature/controller concern. A clip boundary is not
the same thing as the underlying media element naturally reaching its end.

26.11 HLS / SOURCE LIFECYCLE AND MEDIA ERRORS

Keep the settled source support:
- .m3u8 -> HLS path
- progressive .mp4/.webm/etc. -> native video path

The media controller/source hook should:
- use native HLS where the browser supports the required HLS playback directly
- otherwise create hls.js only when an HLS source requires it
- attach the source/media cleanly
- destroy the Hls instance when the source changes or player unmounts
- remove all event listeners during cleanup
- distinguish temporary buffering from fatal/unrecoverable playback failure
- expose a normalized player/media error state suitable for the player UI

Do not leak Hls instances or media listeners across source changes/unmounts.

26.12 PLAYER LOADING / BUFFERING STATUS

Represent player readiness explicitly enough to distinguish initial loading,
ready playback, temporary buffering, and fatal error. A suitable model is
conceptually:

    "idle" | "loading" | "ready" | "buffering" | "error"

or an equivalent smaller state model such as isBuffering + mediaError if that
proves cleaner in implementation.

Do not show a giant blocking loading modal for every short buffering event.
Use an appropriate spinner/loading indication over the player for temporary
buffering and a distinct recoverable/error UI for actual failures.

26.13 PERSISTED PLAYER PREFERENCES

Persist these user preferences in localStorage:
- volume
- muted state
- playback rate

Do NOT persist these merely as player preferences:
- fullscreen state
- theater state
- open learning modal state
- current playback position

Playback-position persistence/resume may be added later only as a deliberate
progress/resume feature.

Read persisted preferences defensively and fall back to sensible defaults if
storage is unavailable or invalid.

26.14 THEATER MODE OWNERSHIP

Keep theater mode.

Fullscreen is primarily a browser/player concern through the Fullscreen API.
Theater mode changes the surrounding page layout, so expose isTheater /
toggleTheater through the player state while allowing the player shell/page
layout to react to it.

Do not make the low-level <video> element/component responsible for knowing the
whole page layout.

26.15 KEYBOARD SHORTCUT ROUTING

Use one clear keyboard-shortcut controller for the player rather than scattered
or duplicated document listeners. Prefer player-scoped keyboard handling so
shortcuts apply when the player is the active context.

Ignore normal player shortcuts when focus is inside an input, textarea, select,
or contenteditable element, unless that particular control explicitly defines a
safe behavior.

When the learning modal is OPEN:

    Enter        -> close modal
    ArrowLeft    -> previous sense
    ArrowRight   -> next sense

When the learning modal is CLOSED:

    Enter        -> open current-cue learning modal if mappings exist
    Space / K    -> play/pause
    J            -> seek backward using the established keyboard seek amount
    L            -> seek forward using the established keyboard seek amount
    ArrowLeft    -> seek backward using the established keyboard seek amount
    ArrowRight   -> seek forward using the established keyboard seek amount
    M            -> mute/unmute
    F            -> fullscreen
    T            -> theater mode

The same keys may intentionally have different meanings while the learning modal
is open. Centralizing shortcut routing makes this state-dependent behavior
explicit and testable.

Visible controls must continue to exist for important shortcut-only actions so
the player is not keyboard-exclusive.

26.16 RECOMMENDED PLAYER COMPONENT BOUNDARIES

Keep components/modules small and responsibility-focused. A reasonable target
structure is:

    VideoPlayer/
      VideoPlayer.tsx
      PlayerProvider.tsx

      core/
        playerStore.ts
        useMediaController.ts
        useHls.ts
        useKeyboardShortcuts.ts
        useActiveCue.ts

      subtitles/
        SubtitleOverlay.tsx
        SubtitleCue.tsx
        SubtitleToken.tsx

      controls/
        PlayerControls.tsx
        Timeline.tsx
        VolumeControl.tsx
        PlaybackRate.tsx
        FullscreenButton.tsx
        TheaterButton.tsx

      learning/
        LearningModal.tsx
        SenseView.tsx
        SenseNavigation.tsx

Exact filenames may change during implementation. The architectural goal is the
important part: VideoPlayer should primarily compose focused pieces rather than
owning hundreds of lines of unrelated state, effects, event listeners, subtitle
matching, modal logic, and control handlers.

26.17 PLAYER STATE OWNERSHIP RULE OF THUMB

Use this ownership model when deciding where new player state belongs:

- HTMLMediaElement: actual media playback truth
- media/player controller: imperative video/HLS integration and lifecycle
- player-scoped Zustand: shared reactive player UI/interaction state
- local React component state: state used by only one small component
- parsed subtitle/mapping model: canonical domain data, not DOM-derived state
- Django/apiClient: persisted learner/server state and mutations

Do not move state into Zustand solely to avoid passing one or two sensible props.
Use it where state/actions are genuinely shared across player subsystems.

27. FRONTEND API TYPES — HANDWRITTEN TYPE ALIASES (DECIDED)

Use handwritten TypeScript API request/response types based on the documented

Do NOT introduce OpenAPI/type generation for V1 merely to generate frontend API

WordSenseMapping CREATE uses `senses`, while UPDATE uses `sense_ids`; model these
as separate request types.

Frontend-only view models/player types may be separate from raw API response
types when transformation improves clarity. Do not pretend a transformed
frontend model is the literal Django response shape.

When the Django API contract changes, update the centralized handwritten types
and the affected frontend code together.

Testing is part of the implementation plan rather than an optional final polish
step.

Use:
- Vitest for unit tests
- React Testing Library for important React component/interaction tests
- Playwright for critical browser/end-to-end flows

Do not attempt to test every trivial presentational component. Concentrate tests
on logic and flows where regressions would be costly or difficult to notice.

28.1 UNIT / INTEGRATION TEST PRIORITIES

High-value Vitest / React Testing Library targets include:
- shared VTT parser
- shared tokenizer
- cue/token identity and position_in_cue behavior
- mapping-to-token matching
- active-cue lookup, including seeking/binary-search fallback
- player-scoped Zustand actions/state transitions
- keyboard shortcut routing, especially modal-open vs modal-closed behavior
- playback restoration around the learning modal
- local removal of a mapping highlight only after the final sense is confirmed
  learned
- apiClient error normalization
- apiClient 401 refresh/retry-once behavior
- concurrent 401 single-flight refresh behavior
- relevant form validation and mapping-editor selection logic

For media-controller tests, mock browser media/HLS boundaries where appropriate;
do not make ordinary unit tests depend on real streaming media.

28.2 PLAYWRIGHT CRITICAL FLOWS

At minimum, prioritize browser tests for:

Authentication/session:
- login and protected-route behavior
- expired access token -> successful refresh -> original flow continues
- failed refresh -> user ends at /login without a refresh loop

Learner player:
- section player loads
- progressive/HLS path can reach usable playback in the relevant test setup
- play/pause, seek, mute, playback rate, theater/fullscreen controls as feasible
- subtitle highlight interaction opens the correct mapping
- opening learning modal pauses and closing restores the correct prior state
- Enter current-cue mode and Left/Right sense navigation
- successful set_learned updates modal state and removes the mapping highlight
  only when its final remaining sense is learned

Admin mapping editor:
- transcript/VTT loads into canonical tokens
- click/tap-style selection can select multiple occurrences/cross-cue words
- mapped occurrences cannot be placed into overlapping mappings
- create mapping with selected subtitle occurrences + senses
- edit senses on an existing mapping
- add/remove occurrences where supported
- delete mapping
- unsaved-work navigation warning

Vocabulary:
- manual sense selection and representative bulk actions

Do not require every browser engine/media codec combination in the first test
suite if that makes tests brittle. Keep core deterministic logic heavily tested
outside E2E and use Playwright for representative real user flows.

28.3 TESTABILITY AS AN ARCHITECTURAL REQUIREMENT

The player/controller/store split should make behavior testable without mounting
the entire application. The VTT parser/tokenizer must be pure enough to test
with small fixtures. Keyboard routing and state transitions should be testable
without relying on scattered global event listeners.

The coding AI should build features in reasonably small increments and add the
high-value tests alongside the relevant implementation rather than generating
the entire frontend first and attempting to retrofit tests afterward.

29. ADDITIONS TO THE UPDATED CORE FRONTEND SUMMARY
===============================================================================

    Video-player internals:
        player-scoped Zustand store, not a global singleton
        HTMLMediaElement remains playback source of truth
        controller owns videoRef / HLS / media listeners / imperative media work
        narrow Zustand selectors prevent currentTime from rerendering everything
        active cue uses indexed progression + binary-search fallback after seek
        subtitles consume canonical parsed data and remain mostly presentational
        one consistent learner highlight style; admin may use mapping colors
        controls auto-hide during inactive playback
        learning modal disables underlying player interaction while open
        normal media ending and future clip-range ending are separate concepts
        persist volume/mute/playback-rate only
        theater state may affect the surrounding player/page shell
        keyboard shortcuts are centralized and modal-state-aware

    API TypeScript types:
        handwritten from the documented Django contract
        centralized rather than duplicated in components
        use `type`, not `interface`
        preserve distinct backend request/response shapes

    Testing:
        Vitest + React Testing Library for high-value logic/components
        Playwright for critical authentication, learner-player, admin-editor,
        and vocabulary flows
        prioritize parser/tokenizer/player/auth/mapping behavior over trivial UI

All decisions in Sections 23-25 remain in force. Sections 26-29 add detail to
those decisions and must not be interpreted as removing any unrelated settled
