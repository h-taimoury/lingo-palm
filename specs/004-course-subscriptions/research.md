# Research: Course Subscriptions

## ZarinPal checkout and recovery

**Decision:** Use ZarinPal v4 hosted checkout with separate sandbox and live configurations. The sandbox accepts a generated UUID as a merchant ID. Use an integer amount in explicit IRR for both the request and verification. The configured plan is shown in tomans. Compare the charge shown at the bank with the advertised price and configure merchant-paid gateway fees. [Sandbox](https://www.zarinpal.com/docs/paymentGateway/sandBox) · [Checkout and verification](https://www.zarinpal.com/docs/paymentGateway/connectToGateway)

**Rationale:** Save the order before requesting checkout, then persist the returned authority before exposing the payment URL to the buyer. A lost request response cannot lead to a customer payment through our app if no URL was delivered. Take the amount from the order when verifying. Use a bounded timeout on provider calls. A verification timeout remains unresolved. When Verify returns success or already verified for the stored authority and amount, finish the local order if it has not been fulfilled. Serialize fulfillment and staff grants by locking the account row with PostgreSQL, and recheck the order under lock before extending access. Keep network calls outside the database transaction.

**Recovery:** Use a scheduled Django command to scan unsettled orders independently of the buyer. Inquiry can tell us an order is paid or verified, and Verify is the authority for fulfillment. Preserve orders after missing callbacks and transport errors. Handle provider-confirmed failure or reversal without granting access. Alert staff to old unresolved orders and verification errors that need review. Start with merchant-initiated bank verification so that only the app initiates final verification and unverified charges can be returned by the provider when its window expires. Verify the merchant setting, allowed verification window, request limits, and already-verified response before going live. Run recovery frequently enough to finish within the confirmed window, including retries. [Inquiry](https://www.zarinpal.com/docs/paymentGateway/otherMethods/Inquiry) · [Verification modes](https://www.zarinpal.com/docs/paymentGateway/moreFeatures/session-validation)

**Alternatives considered:** Handling only the browser return would miss successful purchases. The merchant-wide list of unverified payments omits verified orders and is capped. Per-order recovery also handles a crash between provider verification and the local save. [Unverified payments](https://www.zarinpal.com/docs/paymentGateway/otherMethods/unVerified)

## Access and media

**Decision:** Apply a shared Django access rule across course details, sections, taught senses, subtitle mappings, and section media. Keep published catalog metadata separate from protected content. Make the learner catalog routes guest-capable and preserve sign-in for account, dictionary, and personal vocabulary routes.

**Rationale:** Production publishes bundled subtitles through `backend/config/static_files.py`. Development exposes media through `backend/config/urls_development.py`. The Next media proxy relays arbitrary backend media paths, the player receives the raw hosted video URL, and `frontend/public/sample-courses/` contains public lesson assets. Remove paid lesson assets from these public routes and update both the learner player and staff subtitle editor to use authorized section routes. Support range requests and protect HLS child segments where applicable. Route video from private storage or an origin that serves only the trusted backend. Keep public thumbnails and shared dictionary audio separate. Restrict upstream media requests to configured storage and keys so the relay cannot fetch arbitrary URLs. Check previously published URLs during rollout. The app cannot revoke copies people already downloaded.

**Alternatives considered:** Hiding links in the UI or proxying a video from a still-public origin leaves the original URL accessible. Test the design using private fixtures first. The production media host must prove that it can serve through an authorized route while denying direct public requests. Choosing that host is a deployment decision.

## Deployment

The repo's Render configuration is for a free demo. Confirm that the selected production backend can run recovery on schedule and connect to ZarinPal from approved outbound IPs. Verify the terminal accepts the registered domain and the callback lands on it. Use a separate test environment and database for sandbox payments. Keep public live checkout closed through the private production purchase and settlement check.
